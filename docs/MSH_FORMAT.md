# Earth 2150 MSH format

This describes the files emitted by the 6 October 1999 build of
`Aod2Msh.exe` in this directory. It was derived from the converter's parser and
writer routines and checked against `EDUST1.aod`/`.msh`,
`EDWCA1.aod`/`.msh`, `EDBBC.aod`/`.msh`, `UCSUHL3.aod`/`.msh`, and synthetic
dynamic AOD files. It was additionally checked against an 18,079,220-byte
official corpus of 1,149 historical MSH files; all parse exactly to EOF. Source
AODs are unavailable for that corpus, including `edbpp.msh`, `LCUFG3.msh`, and
`EDUA22.msh`, so corpus-only claims are limited to serialized layout. The
dynamic source checks cover all 92 supplied smoke/PY/PYSHT sources after the
grammar normalization described below; 90 produce valid MSH files and two are
invalid source artifacts.

All integer and IEEE-754 single-precision fields are little-endian. Records are
packed without alignment. In particular, a field following a variable-length
string or the one-byte barrel angle can be unaligned.

## Terminology

- **Base header**: the common `MESH` record used by both static and dynamic
  files. Its on-disk size is `0x368` bytes, including `MESH` and the version.
- **Source object**: an `Object` section in the AOD file.
- **Render object**: one serialized geometry/material record. A source object
  using multiple material IDs produces multiple linked render objects.
- **Offset**: unless stated otherwise, an offset relative to the first byte of
  the relevant record.

## Top-level identification

The first dword distinguishes the two formats generated by the converter.

### Static geometry/animation file

| Offset | Size | Type | Meaning |
|---:|---:|---|---|
| `0x00` | 4 | `u32` | Archive framing value `0x20D0A1FF` |
| `0x04` | 16 | bytes | Raw Windows GUID generated by `CoCreateGuid` |
| `0x14` | `0x368` | `BaseHeader` | Common `MESH` header |
| `0x37C` | 4 | `u32` | Trailing source-hierarchy unwind count; see below |
| `0x380` | variable | `StaticObject` | First render object; linked objects follow recursively |

The GUID is stored as the raw in-memory 16-byte `GUID`. Consequently, the
first three canonical GUID fields use Windows GUID byte order. It changes on
every conversion and is not a content hash.

### Dynamic effect file

| Offset | Size | Type | Meaning |
|---:|---:|---|---|
| `0x00` | 4 | `u32` | Archive framing value `0x30D0A1FF` |
| `0x04` | 4 | `u32` | Archive type, always `1` in generated files |
| `0x08` | 16 | bytes | Raw Windows GUID |
| `0x18` | variable | `DynamicObject` | Root dynamic object |

The low 24 bits of both framing values are the archive signature `0xD0A1FF`.
The upper byte is a bitfield produced by the converter's stream class, not part
of the `MESH` magic.

## Common base header

This table is relative to the `MESH` bytes: static file offset `0x14`, dynamic
file offset `0x18`, or the beginning of a nested dynamic object.

| Offset | Size | Type | Meaning |
|---:|---:|---|---|
| `0x000` | 4 | char[4] | ASCII `MESH` |
| `0x004` | 4 | `u32` | Format version, `1` |
| `0x008` | 4 | `u32` | Mesh kind: `0` static, `1` dynamic |
| `0x00C` | 4 | `u32` | 4x4 box/cell presence mask |
| `0x010` | 4 | `u32` | Four reverse-packed 8-bit animation lengths |
| `0x014` | 4 | `u32` | Header flags/reserved; zero in all supplied files |
| `0x018` | `0xF0` | bytes | Spot-light record area, formula below |
| `0x108` | `0x70` | bytes | Remaining light record storage/overlap area |
| `0x178` | `0x20` | `u16[16]` | Box heights, physically reverse-indexed |
| `0x198` | `0x10` | `u8[16]` | Box flags, physically reverse-indexed |
| `0x1A8` | `0x10` | `u32[4]` | Derived 4x4-grid coverage descriptors |
| `0x1B8` | `0x20` | `u64[4]` | Derived 4x4-grid coverage bitmaps |
| `0x1D8` | `0x188` | `Attachment[49]` | Slot/light attachment records 1 through 49 |
| `0x360` | 8 | `u16[4]` | Horizontal extents: `+Y`, `-Y`, `+X`, `-X` |

The converter's in-memory base class contains a pointer between the coverage
descriptors and bitmaps. The writer deliberately skips that pointer, which is
why some decompiled in-memory offsets differ by four bytes after this point.

### Animation-length dword

Animation type `n` is stored in byte `3-n` of the dword at `0x010`, for
`n = 0..3`. Equivalently:

```text
animation_lengths |= (frame_count & 0xFF) << (8 * (3 - animation_type))
```

The `Animation 2, 6` section in `EDWCA1.aod` therefore produces `0x00000600`.
The three `Animation 0, 48` sections in `EDBBC.aod` produce `0x30000000`.
Multiple objects of one type rewrite the same byte; they are expected to use
the same frame count.

The object naming convention and the AOD exporter use type `2` for the `C`
(non-looped) animation shown in the supplied documentation. Types `0`, `1`,
and `2` correspond to the A/B/C animation classes. Type `3` is also present in
the official binary corpus with declared lengths 16, 46, and 51, although no
source AOD for those files is available.

### Box records

For logical box index `i` in `0..15`:

```text
height[i] is u16 at base + 0x196 - 2*i
flags[i]  is u8  at base + 0x1A7 - i
```

For AOD coordinates `(x,y,z)`, the converter computes:

```text
i = 15 + 4*trunc(y) - trunc(x)
height[i] = trunc(z * 256)
```

Here and below `trunc` means truncation toward zero. The box sets bit `i` in the
dword at `0x00C` and packs its four AOD boolean values into bits 0 through 3 of
`flags[i]`. `EDBBC` maps its four boxes to indices `11`, `15`, `10`, and `14`
in source order, producing mask `0x0000CC00`; their flags are respectively
`1`, `2`, `8`, and `4`, and their truncated heights are `380`, `380`, `493`,
and `380`.

`edbpp.msh` has explicit box mask `0x0000C000`: boxes 14 and 15 have heights
`239` and `416`, and both box flag bytes are zero. A present box therefore does
not require any of its four AOD boolean values to be set; presence comes only
from the mask.

The coverage values at `0x1A8` and `0x1B8` are derived from all 16 cells; they
are not direct AOD arrays. If the AOD supplies no boxes, the converter sets bit
15 as the default single-cell footprint, calls `compute_mesh_max_z`, and stores
`trunc(max_z * 256)` as box 15's height with flags zero. This is why `EDUST1`,
`EDWCA1`, `UCSUHL3`, and `LCUFG3` contain `0x00008000`. `LCUFG3` provides a
simple check: maximum serialized Z is approximately `0.452`, producing height
`115`.

### Explicit-box recentering

When the AOD supplies a `Boxes` section, the converter performs a post-parse
horizontal recenter before serialization. It subtracts `0.5` from game X and Y
for root-level vertices, nested object pivots, baked translation tracks, spot
and omni light positions, cannon positions, and applicable quantized
attachments. Quantized coordinates are adjusted by `-0x80`.

This is why an `EDBBC` source vertex `(1.208,-1.586,0.578)` is stored as
approximately `(0.708,1.086,0.578)`, and child position
`(0.9564801,-0.9897320,1.1861143)` is stored as
`(0.4564801,0.4897320,1.1861143)`. Files using only the synthesized default box
do not receive this half-cell recenter.

### Horizontal extents

The final four words are nonnegative 8.8 fixed-point extents from root-level
geometry:

```text
word 0 = trunc(max_y * 256)
word 1 = trunc(-min_y * 256)
word 2 = trunc(max_x * 256)
word 3 = trunc(-min_x * 256)
```

For example, `EDWCA1` has approximately +/-0.168 Y and +/-0.192 X, producing
`43, 43, 49, 49`.

`EDUA22` confirms that nested geometry is excluded. Its nested rotor spans
`-0.5..+0.5` in X, but the stored positive-X extent is only `99/256`, matching
the root-level maximum near `0.389`; the root's negative-X maximum near
`-0.665` produces `170/256`.

## Attachments and slots

Each attachment is eight bytes:

| Relative | Size | Type | Meaning |
|---:|---:|---|---|
| `+0x00` | 2 | `i16` | `trunc(x * 256)` |
| `+0x02` | 2 | `i16` | `trunc(-y * 256)` |
| `+0x04` | 2 | `i16` | `trunc(z * 256)` |
| `+0x06` | 1 | `u8` | Heading, one full turn = 256 |
| `+0x07` | 1 | `u8` | Raw extra byte; generated slots use the quantized angle described below |

Attachment index `i` is at:

```text
base + 0x1D0 + 8*i
```

The meaningful generated range is `i = 1..49`; it occupies the documented
`0x1D8..0x35F` area. Unset records are identified only by `0x8000` in all three
coordinates. Their heading and extra angle remain independent serialized
values.

The heading is derived from the AOD slot's second point with angular scale
`128/pi`, equivalent to 256 units per turn. The extended nine-parameter `Slot`
syntax converts its final angle with `trunc(angleRadians * 128 / pi) & 0xFF`;
the ordinary six-coordinate syntax uses `0x80`, or pi radians. Convert the
stored extra angle back with `byte * pi / 128` radians or `byte * 360 / 256`
degrees. Negative inputs wrap into the unsigned byte; for example, `0xB1` is
248.906 degrees, equivalent to -111.094 degrees.

Confirmed extra-angle bytes in official cannon-slot (`BC`/`SC`) records are
`00 0F 15 1C 20 31 40 47 4E 55 5C 60 71 78 80 B1`; most attachment records use
the ordinary `0x80` default. The exact runtime meaning remains unconfirmed
beyond being an angular property associated with cannon slots. Zero bytes in
attachment records 13 through 17 are generally generated by spot lights and
are not slot-angle parameters.

The converter's slot table is:

| AOD code | Maximum number | Base index | Additional effect |
|---|---:|---:|---|
| `BC` | 4 | 0 | Stores one of four cannon positions |
| `SC` | 4 | 0 | Alias of the same cannon-position range |
| `MI` | 4 | 4 | Sets object marker bit `0x1000 << (number-1)` |
| `SS` | 4 | 8 | None |
| `TR` | 4 | 20 | None |
| `HT` | 4 | 24 | None |
| `SM` | 4 | 28 | None |
| `WT` | 4 | 32 | None |
| `CH` | 2 | 36 | None |
| `ST` | 2 | 38 | None |
| `SE` | 2 | 40 | None |
| `SK` | 2 | 42 | None |
| `IN` | 1 | 44 | None; supplied AOD uses number 0 |
| `CE` | 1 | 45 | None; supplied AOD uses number 0 |
| `PR` | 1 | 46 | None |
| `MV` | 1 | 47 | None |
| `LN` | 1 | 48 | None; this appears to be the documented landing slot |

The record index is `base index + effective number`. Numbers are normally
one-based. For a slot type whose maximum is one, AOD number zero is accepted
and coerced to effective number one. Thus `IN,0` uses record 45 and `CE,0` uses
record 46 despite the table's base indices 44 and 45.

Light parsing also writes quantized positions into this attachment area. Spot
light number `n` uses the record at common-header memory offset
`0x238 + 8*n`, and omni light number `n` uses `0x258 + 8*n`. On disk these are
base offsets `0x230 + 8*n` and `0x250 + 8*n`. These ranges can overlap rarely
used numbered slot records; this is behavior of the original converter.

## Light record area

The AOD parser supports two `Light` line shapes.

### Spot form

Spot light number `n` uses a 48-byte record at:

```text
base + 0x018 + 0x30*n
```

The `n = 0` 48-byte region is also treated as four consecutive 12-byte cannon
position vectors. `LCUFG3` confirms that these are the full-precision forms of
`BC1..BC4`; its four vectors quantize exactly to attachment records 1..4.
Supplied numbered spot lights begin at 1.

| Record offset | Size | Type | Meaning |
|---:|---:|---|---|
| `0x00` | 12 | `float[3]` | Position `(x, -y, z)` |
| `0x0C` | 12 | `float[3]` | Three AOD light parameters |
| `0x18` | 4 | `float` | Approximate horizontal target distance |
| `0x1C` | 1 | `u8` | Target heading, 256 units per turn |
| `0x1D` | 3 | bytes | Zero/padding from a dword store |
| `0x20` | 4 | `float` | Tangent of half the cone angle |
| `0x24` | 4 | `float` | Distance-scaled cone parameter |
| `0x28` | 4 | `float` | Vertical slope to target |
| `0x2C` | 4 | `float` | Final AOD light parameter |

The exact game-facing names of the secondary light parameters are not present
in the binary. Their widths, formulas, and positions above are confirmed. The
documentation describes them as color/brightness/cone/length controls.

The public model preserves the first vector as `Position` and the second as
`LightParameters`. It exposes the remaining values with neutral format-derived
names and keeps the heading byte separate from all three reserved bytes. No
light parameter passes through an 8-bit color representation.

### Omni form

Omni light number `n` uses a 28-byte record at:

```text
base + 0x0EC + 0x1C*n
```

It contains two `(x, -y, z)` float vectors at `+0x00` and `+0x0C`, followed by
one float at `+0x18`. As with spot lights, its first position is also emitted as
an eight-byte quantized attachment record.

The spot and omni formulas intentionally address a partially overlapping common
area. Files should follow the converter's expected light-number ranges rather
than treating the area as two unconstrained arrays.

The explicit-box recenter pass visits fixed light and cannon-position storage,
not only records known to be active. In `edbpp.msh`, unused spot positions 2..4
are therefore `(-0.5,-0.5,0)` rather than zero. The four unused cannon-position
vectors in the overlapping first 48 bytes have the same value. Consumers must
not infer active lights or cannons from these position values alone.

EarthTool determines static light activity from attachment records 13..16 for
spot lights and 17..20 for omni lights. MSH writing preserves full-precision
light and quantized attachment positions independently.

### COLLADA static-light contract

Active records export with stable names `SpotLight-1` through `SpotLight-4` and
`OmniLight-1` through `OmniLight-4`; inactive records are omitted without
compacting gaps. Standard COLLADA color is white. Position and the spot cone
angle, calculated as twice the arctangent of the stored half-angle tangent, are
the only projected standard values.

The complete record is stored as invariant round-trip text in an unqualified
`msh_static_light` element with `version="1"`, nested under an `EARTHTOOL`
technique in `extra`. Its `source_number` must agree with the numbered light
name. Import rejects malformed or incomplete metadata, unsupported versions,
conflicts, duplicates, out-of-range numbers, and excess records. If metadata is
absent, import requires the same numbered names, uses standard COLLADA color as
`LightParameters`, maps only confirmed fields, and zeroes the rest. When an
active imported position quantizes to all three `0x8000` sentinel coordinates,
only the attachment X coordinate is moved by one fixed-point unit; the complete
light record retains its exact position.

`EDBBC` validates multiple spot records and the explicit-box recenter. Its
light 1 source position `(0.320,-1.390,0.463)` is stored approximately as
`(-0.180,0.890,0.463)` and as attachment 13 raw coordinates
`(-47,227,118)`. Light 2 is stored approximately as
`(0.503,-0.284,0.463)` and attachment 14 `(128,-73,118)`.

`UCSUHL3` validates five ordinary slots and one spot-light attachment without
explicit-box recentering. `BC1`, `HT1`, `SM1`, `IN0`, and `CE0` occupy records
1, 25, 29, 45, and 46. Spot light 1 occupies record 13. Their raw positions are
respectively `(-15,0,163)`, `(-22,0,139)`, `(-31,0,156)`, `(-24,0,240)`,
`(-10,0,0)`, and `(44,25,141)`, confirming the existing index table,
zero-to-one coercion, Y negation, and truncation rules.

`edbpp.msh` exercises fuller attachment ranges: `HT1..HT4` occupy records
25..28, `SM1..SM4` occupy 29..32, `CH1` occupies 37, and `IN0`/`CE0` occupy
45/46. Spot light 1 adds record 13, for twelve active records total. Its
headings include `63`, `127`, `192`, and `255`, illustrating truncation near
quarter-turn boundaries rather than rounding.

`LCUFG3.msh` has `BC1..BC4` in records 1..4, spot lights 1..3 in records
13..15, plus `HT1`, `SM1`, `IN0`, and `CE0` in records 25, 29, 45, and 46.
This yields eleven active attachments and confirms that multiple numbered spot
lights use consecutive attachment records.

`EDUA22.msh` has one cannon/`BC`-range attachment at record 1, spot light 1 at
record 13, and `HT1`, `SM1`, `IN0`, and `CE0` at records 25, 29, 45, and 46.
Record 1 has extra byte zero rather than the ordinary `0x80`, consistent with
the extended slot syntax supplying an explicit quantized angle.

## Static render object

Static records are variable-length and linked by the writer's recursive
next-record pointer. Read fields in the following order using a moving cursor.

| Order | Size | Type | Meaning |
|---:|---:|---|---|
| 1 | 4 | `u32` | Render vertex count `V` |
| 2 | 4 | `u32` | Vertex block count `B`; generated value is `ceil(V/4)` |
| 3 | `B*0xA0` | `VertexBlock[B]` | Blocked vertex channels |
| 4 | 4 | `u32` | Object flags |
| 5 | 4 | `u32` | Texture-path byte length `L` |
| 6 | `L` | bytes | ASCII texture path, no NUL and no padding |
| 7 | 4 | `u32` | Triangle/index record count `T` |
| 8 | `T*8` | `Triangle[T]` | Triangle records |
| 9 | 4 | `u32` | Scale-track count `S` |
| 10 | `S*12` | `float[S][3]` | Baked `TcbScale` track |
| 11 | 4 | `u32` | Translation-track count `P` |
| 12 | `P*12` | `float[P][3]` | One translation vector per baked frame |
| 13 | 4 | `u32` | Matrix count `M` |
| 14 | `M*64` | `float[M][16]` | Baked 4x4 transform matrices |
| 15 | 4 | `u32` | Animation type |
| 16 | 12 | `float[3]` | Object pivot/position `(x, -y, z)` |
| 17 | 1 | `u8` | Barrel maximum angle, 256 units per turn |
| 18 | 4 | `u32` | Next-record marker |
| 19 | variable | `StaticObject` | Present immediately if the marker is nonzero |

There is no terminator after the last object. The final next-record marker is
zero and must bring the parser exactly to EOF.

### Next-record marker warning

The converter writes its live 32-bit heap pointer as the next-record marker
instead of normalizing it to `1`. For example, reconverting `EDUST1.aod` produced
different nonzero values at this field on each run while every other
non-generated static byte remained equal. Treat this dword strictly as a
boolean. It is process-address noise, not an offset and must never be
dereferenced or relocated.

Despite the writer's recursive implementation, this marker links the next
render record in one linear sequence. That record may represent a child source
object, a sibling after hierarchy levels close, or another material partition
of the same source object. It is not necessarily a direct child of the
preceding record.

### Vertex block

Each `0xA0`-byte block stores up to four vertices in structure-of-arrays form.
For lane `i = 0..3`:

| Block offset | Type | Meaning |
|---:|---|---|
| `0x00 + 4*i` | `float` | X |
| `0x10 + 4*i` | `float` | Y, already converted to game coordinates |
| `0x20 + 4*i` | `float` | Z |
| `0x30 + 4*i` | `float` | Normal X |
| `0x40 + 4*i` | `float` | Normal Y, already converted |
| `0x50 + 4*i` | `float` | Normal Z |
| `0x60 + 4*i` | `float` | Texture U |
| `0x70 + 4*i` | `float` | Texture V, generated as `1 - AOD_V` |
| `0x80 + 4*i` | `float` | Third texture component/reserved; generated as zero by the original converter and preserved raw by EarthTool |
| `0x90 + 2*i` | `u16` | Earlier render vertex sharing the normal, or `0xFFFF` |
| `0x98 + 2*i` | `u16` | Earlier render vertex sharing the source position, or `0xFFFF` |

Unused lanes in the final block retain zero/default values. Readers must use
`V`, not `B*4`, as the real vertex count.

The converter does not serialize the AOD vertex, UV, and normal arrays
separately. For each material it interns unique `(vertex index, UV index,
normal index)` tuples into render vertices. A position split by UV seams or
hard normals therefore appear more than once.

### Triangle record

| Offset | Size | Type | Meaning |
|---:|---:|---|---|
| `0x00` | 2 | `u16` | Render vertex 0 |
| `0x02` | 2 | `u16` | Render vertex 1 |
| `0x04` | 2 | `u16` | Render vertex 2 |
| `0x06` | 2 | `u16` | Triangle flags |

| Bit | Generated meaning |
|---:|---|
| `0x0001` | Base bit, set unconditionally for every emitted triangle |
| `0x0002` | Upward-surface bit, set when the recomputed normalized face Z is strictly greater than `0.5` |

The flags are generated by `parse_static_object`; they are not copied from the
AOD `FaceList`. For serialized render positions `p0`, `p1`, and `p2` in index
order, the exact calculation is:

```text
a = p1 - p0
b = p2 - p1
n = normalize(cross(b, a))

flags = 0x0001
if n.z > 0.5:
    flags |= 0x0002
```

The calculation uses the geometry after AOD-to-game coordinate conversion and
does not use the three per-vertex normals. Bit `0x0002` therefore identifies an
upward-wound surface whose geometric normal is within 60 degrees of +Z,
equivalently a plane tilted less than 60 degrees from horizontal. Vertical,
downward-facing, and steeper surfaces retain value `1`. Degenerate triangles
also retain `1` because normalizing their zero cross product yields an unordered
floating-point result and the strict comparison fails.

This derivation describes the original AOD-to-MSH converter. EarthTool exposes
the complete word as unsigned `Face.Flags` and preserves it verbatim when an MSH
is read and written; it does not recompute the flags from geometry. Importers
that have no original MSH flag metadata must generate a value instead; the
current COLLADA importer uses the base value `0x0001`.

The producer behavior is fully determined, but the runtime interpretation of
the unconditional base bit remains unknown because no game-side MSH reader is
available in this corpus. It should not be named `visible`, `collidable`, or
`walkable` without consumer evidence.

### Object flags

Confirmed high bits are:

| Bit | Meaning/source |
|---:|---|
| `0x00000100` | Nonzero AOD `ViewerFaced` |
| `0x00000200` | AOD `Barrel` is present/nonzero |
| `0x00000400` | Nonzero AOD `Rotor` |
| `0x00000800` | First material partition of a nested source object |
| `0x00001000..0x00008000` | Numbered special marker, notably `MI1..MI4` |

Across all 3,088 official static render records, every set flag bit is either
one of these high bits or part of the low-byte unwind count. No unknown flag
bits were observed. The largest observed unwind is 5 and the largest
reconstructed source depth is 7, both in `EDUTA1.msh`.

The low byte is the hierarchy unwind count applied at that record. The
converter and its explicit-box recenter pass reconstruct source depth while
walking the linear record chain as follows:

```text
depth = 0
for each render record:
    if flags & 0x00000800:
        depth += 1
    depth -= flags & 0xFF
    process record at depth
```

Additional material partitions of the same source object do not set
`0x00000800`. For a new sibling, the first partition both sets that bit and
unwinds the levels closed since the previous source object. A partition emitted
after returning to an ancestor has only the unwind count. `EDBBC` exercises all
three cases. `UCSUHL3` has source depths `0,1,2,3,1,2,3`; its fifth record has
flags `0x00000803`, which opens a nested object and closes three prior levels,
returning from depth 3 to depth 1. Preserve the low byte when round-tripping.

### Trailing hierarchy unwind count

The dword at static file offset `0x37C` is the pending hierarchy unwind after
the final render record, not an object count. `parse_static_object` maintains a
shared accumulator using this logic:

```text
pending_unwind = 0

before emitting a record after completed source objects:
    record.flags.low_byte |= pending_unwind
    pending_unwind = 0

when a source Object section finishes:
    pending_unwind += 1

after the final record:
    file[0x37C] = pending_unwind
```

The executable performs the final increment at `0x0040A42F` and writes the
accumulator from converter-object offset `0x5D4` at `0x0040B1E7`.

The first render record of a nested object consumes the pending value while
also setting `0x00000800`. A later material partition of an ancestor consumes
it without setting the nested-object bit. If no later record exists, the value
cannot be carried in record flags and remains in the fixed header as the
virtual unwind at EOF.

Because valid AOD geometry has exactly one main root object, this gives a simple
reader invariant:

```text
trailing_unwind_count == final_render_record_source_depth + 1
```

All 955 official static files satisfy this invariant. Their values range from
1 to 7: 699 files store 1, 199 store 2, 28 store 3, 19 store 4, eight store 6,
and two store 7. No file in this corpus stores 5.

This explains the earlier examples. `EDBBC` emits a root material partition
after its children, so the final record is back at depth 0 and the trailing
unwind is 1. `EDWCA1` ends on its depth-1 barrel and stores 2. `UCSUHL3` ends
on a depth-3 leaf and stores 4.

The published [The Moon Project object identifier
list](https://insideearth2150.github.io/Documentation/The%20Moon%20Project/MOON-C/main/identifiers.htm)
contains 20 paired `EDB...` and `EDBB...` building identifiers with the same
display names. This is consistent with the `EDBB...` files being construction
variants: all 20 share animation lengths `(0,81,255,16)`, while the regular
models have model-specific animation declarations. All 20 regular `EDB...`
files store trailing unwind 1; 19 construction variants store 2 and
`EDBBAB.msh` stores 3. The field is not a construction-model discriminator,
however. The variants differ because their final render records are
respectively at depths 1 and 2, whereas the regular models emit a depth-0 root
partition last. Chassis, weapons, equipment, and buildings otherwise share
overlapping trailing-unwind values.

### Materials and hierarchy

The texture path is generated as `Textures\` plus the AOD material's texture
name, preserving its case. It is length-prefixed only.

Faces are partitioned by material ID. Each nonempty material partition becomes
a render object in the same next-record chain as actual source subobjects.
Consequently:

- The trailing unwind at file offset `0x37C` is neither the total number of AOD
  `Object` sections nor the number of serialized render records.
- `EDUST1` has one source object but two render records because it uses two
  material IDs.
- `EDBBC` has four source objects but eight render records: three material
  partitions for the root, two each for `PA2` and `PA1`, and one for `PA3`.
  The resulting texture/triangle sequence is `EDLS:6`, `EDBBC:16`, `EDBR1:12`,
  `EDBBC:16`, `EDBR1:12`, `EDLD:2`, `EDBBC:263`, `SIDECOLORB:6`.
- `UCSUHL3` uses one material, so its seven source objects map one-to-one to
  seven render records. Its two depth-three branches both begin with a sibling
  named `UCSPB4S0E228`; duplicate source names are accepted and object names are
  not serialized.
- `edbpp.msh` has three root-depth render records with textures `EDBPP`,
  `SIDECOLORB`, and `EDLS` and triangle counts 180, 4, and 20. This is
  consistent with one source object split across three materials, but cannot be
  proven without its AOD. All hierarchy flags are zero and its trailing unwind
  is 1.
- `LCUFG3.msh` has two root-depth render records with textures `lcufg` and
  `sidecolor` and triangle counts 179 and 4. Both hierarchy flags are zero and
  the trailing unwind is 1, consistent with a two-material root object.
- `EDUA22.msh` serializes root material `edua2122`, a nested `edurotor` object,
  then root material `sidecolor`. Their triangle counts are 64, 4, and 10. The
  final record's flags contain unwind count 1, returning from source depth 1 to
  depth 0 before emitting the root's remaining material partition.
- A reader must follow next-record markers to EOF; the trailing unwind is not a
  record count.

### Animation fields

The converter expands sparse AOD keys to per-frame arrays. `EDWCA1` has six
frames and its animated barrel record contains six translations and six 4x4
matrices. `TcbRotation` keys are baked into the matrix array; they are not the
12-byte vector track. The first vector track stores interpolated `TCBScale`
keys and is empty in the three earlier static examples.

In `EDBBC`, `PA2` and `PA1` contain rotation keys only and serialize 48 matrices
with no translation or scale vectors. `PA3` contains explicit translation keys
and serializes 48 translations plus 48 matrices. Explicit-box recentering
subtracts `0.5` from the X and game-Y components of those translation vectors.

`UCSUHL3` provides the long type-1 case. Its header stores 229 as raw animation
length dword `0x00E50000`, and all seven render records serialize 229 scales,
229 translations, and 229 matrices. Every source object has only six
`TCBScale` keys at frames `0,7,55,132,180,228`; those unit keys bake to 229
unit vectors. The root supplies all 229 translation keys, while each child has
only six constant translation keys at the same sparse frames; both forms bake
to 229 translation vectors. Thus a present scale or translation channel is
expanded to the declared animation frame count, not serialized as sparse keys.
The root's six identity rotation keys likewise produce 229 identity matrices,
confirming that matrix count follows the baked rotation channel even when every
result is identity.

`EDUA22` provides the opposite case: its header declares type 1 length 32
(`0x00200000`), and the nested rotor record stores animation type 1, but all
three track counts are zero. Animation declaration, frame count, and object
animation type therefore do not imply that scale, translation, or matrix data
is present. Its rotor record has flags `0x00000C00`, combining nested-object and
`Rotor` bits; readers must not treat the `Rotor` bit as evidence of a serialized
matrix track.

Official binaries also exercise animation type 3. The EDBB family declares 16
frames while its type-3 records have no tracks; `LCUTA1.msh` stores 46
translations; `EDUTA1.msh` stores 51 translations in each type-3 record; and
`UCSUTA1.msh` stores 51 translations with matrices present on some records.
Thus type 3 uses the same three optional track arrays and reverse-packed length
rule as the other animation types.

`EDWMM31.msh` is the sole track-length exception in the 955-file official
static corpus. Its header declares type-2 length 12, but one type-2 record
stores 13 translations. The first translation differs, while translations 1
through 12 equal the record position. Every other official track array either
contains the declared count or is empty. Without the source AOD this remains a
historical exporter anomaly; readers must honor each serialized track count
rather than deriving it from the header length.

The stored Y coordinate is negated. The one-byte barrel value uses the same
angular unit as headings:

```text
barrel_byte = trunc(barrel_radians * 128 / pi)
```

`0.3492` radians (approximately 20 degrees) therefore becomes `14`.

The supplied `Animation 2, 6` produces object animation type `2`. Matrix values
are 16 raw little-endian floats in the converter's Direct3D-era matrix layout;
do not transpose the byte stream when parsing.

## Dynamic object

A dynamic object begins with a complete `0x368`-byte common base header. Its
effect extension follows immediately. The offsets below are relative to that
object's `MESH` magic.

| Offset | Size | Type | Meaning |
|---:|---:|---|---|
| `0x368` | 4 | `u32` | Effect type |
| `0x36C` | 4 | `u32` | Light type |
| `0x370` | 4 | `i32` | First source frame |
| `0x374` | 4 | `i32` | Frame count, `last-first+1` |
| `0x378` | 4 | `i32` | Sprite-sheet column count |
| `0x37C` | 4 | `i32` | Sprite-sheet row count |
| `0x380` | 4 | `i32` | Third `Frames` parameter |
| `0x384` | 4 | `float` | `1.0 / column_count` |
| `0x388` | 4 | `float` | `1.0 / row_count` |
| `0x38C` | 16 | `float[4]` | Primary size rectangle |
| `0x39C` | 16 | `float[4]` | Secondary size rectangle |
| `0x3AC` | 4 | `float` | Fifth `Size` parameter; Width uses half-width |
| `0x3B0` | 4 | `float` | Signed half-span `(size[2]-size[0])/2`; Width uses half-width |
| `0x3B4` | 4 | `u32` | Reserved/unknown; generated as zero |
| `0x3B8` | 4 | `u32` | Additive flag |
| `0x3BC` | 12 | `float[3]` | Light vector after scalar multiplication |
| `0x3C8` | 12 | `float[3]` | Color RGB |
| `0x3D4` | 4 | `float` | Fourth `Color` parameter |
| `0x3D8` | 4 | `i32` | Optional third `Alpha` parameter/mode |
| `0x3DC` | 4 | `float` | Second AOD `Alpha` value |
| `0x3E0` | 4 | `float` | First AOD `Alpha` value |
| `0x3E4` | 4 | `float` | Second AOD `Scale` value |
| `0x3E8` | 4 | `float` | First AOD `Scale` value |
| `0x3EC` | 12 | `float[3]` | Position `(x, -y, z)` |
| `0x3F8` | 12 | `float[3]` | Position2 `(x, -y, z)` |
| `0x404` | 4 | `u32` | Mesh-name length `A` |
| `0x408` | `A` | bytes | Mesh name, no NUL |
| next | 4 | `u32` | Texture-path length `B` |
| next | `B` | bytes | Texture path, no NUL |
| next | 4 | `u32` | Dynamic child count `C` |
| next | variable | `DynamicObject[C]` | Complete child records, each beginning `MESH` |

The public properties for these three color-related fields are `LightVector`,
`ColorRgb`, and the separate `ColorParameter`. They preserve raw floating-point
values, including finite values outside `0..1`.

With empty strings and no children, one dynamic record is `0x410` bytes. Each
child is a complete record with its own common base header and effect extension,
but no archive framing or GUID.

### Dynamic AOD grammar compatibility

This converter build expects a dynamic AOD to contain `Dynamic`, followed
directly by `Object`; texture selection is an object property such as
`Texture Fire.tex`. It explicitly rejects a top-level `Materials` section with
`section "Materials" in dynamic mesh is not allowed`.

The supplied smoke/PY sources use a static-exporter-style `Materials 1` wrapper
and omit the object's `Texture` property. They were kept unchanged as source
artifacts. For validation, temporary copies were normalized by removing
`Materials` and moving its sole texture name into the `Object`. This changes
only how the converter receives the texture name; the resulting MSH field is
the ordinary `Textures\name` string documented above.

The root `Object` name must equal the input filename stem. This is why the
supplied `PYLINE.aod` fails as written: it declares `Object PYLASER`. Renaming
that object to `PYLINE` is sufficient for conversion; its `Type Line` is valid.

Symbolic values such as effect and light types are compared with an ASCII
case-insensitive comparator. `Type Line` and `Type line` produce byte-identical
payloads. String-valued lines must otherwise contain exactly the value: the
semicolon annotations in `PYEXP_EXAMPLE.aod` are not comments, and after its
object-name mismatch is fixed, its annotated `Type` line is rejected. That file
also contains unsupported `Length` syntax and should be treated as prose/example
material rather than valid AOD input.

### Dynamic defaults

The 90 generated dynamic base headers are byte-identical. Their logical fields
are zero/defaulted apart from `MESH`, version `1`, and mesh kind `1`; physically,
each of the 49 unset attachment records contains `0x8000` in all three
coordinates as documented in the attachment section. Omitted extension
properties retain these constructor values:

| Property group | Default serialized value |
|---|---|
| Light type | `Const` (`0`) |
| Frames and reciprocals | All zero |
| Primary and secondary size | `(-0.25,0.25,0.25,-0.25)` |
| Fifth size parameter and signed half-span | `0.25`, `0.25` |
| Reserved and additive | `0`, `0` |
| Light vector | `(0,0,0)` |
| Color | `(1,1,1,1)` |
| Alpha | mode `0`, values `(1,1)` |
| Scale | `(0,0)` |
| Position and Position2 | `(0,0,0)` |
| Mesh name, texture name, children | empty, empty, `0` |

Omitting an effect `Type` leaves the constructor value zero. No symbolic
`Type` text maps to zero; unrecognized nonempty type text is rejected.

### Dynamic AOD property transformations

- `Frames first,last,param,columns,rows` stores `first`,
  `last-first+1`, `columns`, `rows`, and `param` in the order shown above.
- `Width w` writes `(-w/2,+w/2,+w/2,-w/2)` to both size rectangles.
- `Width2 w` changes only the secondary rectangle.
- `Size a,b,c,d,e` writes `(a,b,c,d)` to both rectangles, stores `e`, and
  stores `(c-a)/2`.
- `Size2 a,b,c,d` changes only the secondary rectangle.
- `Light r,g,b,k` stores `(r*k,g*k,b*k)`.
- `Color r,g,b,k` stores RGB and `k` separately.
- `Alpha a,b[,mode]` is physically stored as `mode,b,a`.
- `Scale a,b` is physically stored as `b,a`.
- `Position` initializes both positions; `Position2` overrides the second.
- `Mesh name` is stored unchanged. `Texture name` is stored as
  `Textures\name`.

Numeric parsing accepts a valid numeric prefix. In particular, the four
Shockwave examples' `Width 1.0f` is accepted and serialized exactly as width
`1.0`; strict third-party AOD parsers may choose not to accept this suffix.

The 90 normalized source/binary pairs were checked property by property and to
exact EOF. They confirm Explosion (`1`), Laser (`6`), LaserWall (`7`), Shockwave
(`8`), Sphere (`10`), Lighting (`12`), and Smoke (`13`); Const (`0`),
Trapezium (`2`), and Random (`3`) light modes; omitted frames; nonzero first
frames; additive values 0 and 1; scalar-multiplied light vectors; colors; width;
and asymmetric size rectangles. `PY_FIRE_S` additionally confirms that the
field at `0x3B0` is signed: `Size 0.15,...,-0.15,...` stores `-0.15`.

## Coordinate and numeric conventions

- AOD `(x,y,z)` becomes game `(x,-y,z)` for positions, normals, animation
  translations, slots, and lights. An explicit `Boxes` section then applies
  the separate half-cell recenter described above to positional X/Y values,
  but not normals.
- AOD UV `(u,v)` becomes `(u,1-v)`.
- Geometry and animation channels are ordinary 32-bit floats.
- Slots, attachment positions, box heights, and final extents use a scale of
  256 followed by x87 truncation toward zero. The converter temporarily sets
  the x87 rounding-control bits to `11b` before `fistp`.
- Angles use 256 units per full turn (`128/pi` units per radian) and the same
  truncation toward zero.
- There is no byte swapping, compression, checksum, alignment, or offset table.

## Validation and nondeterminism

### Official corpus coverage

The complete official corpus has the following structural coverage:

| Metric | Static | Dynamic |
|---|---:|---:|
| Files | 955 | 194 |
| Serialized records | 3,088 | 445 |
| Maximum records in one file | 47 (`EDBBTC.msh`) | 17 (`PYEXP_RUIN_S.msh`) |
| Maximum reconstructed depth | 7 (`EDUTA1.msh`) | 1 |

Every file uses version 1 and the expected mesh kind, and every static vertex
block count equals `ceil(vertex_count / 4)`. The 86,102 static triangles contain
59,185 flag-1 and 26,917 flag-3 records, including 231 degenerate flag-1
triangles. Recomputing the face normal reproduces every flag with zero
mismatches. The static files contain 19 distinct box masks and between 0 and 35
populated attachments; `XXDEFAULT.msh` supplies the 35-attachment maximum. All
observed object flags fit the documented mask, all four animation types occur,
and the only populated-track/header-length mismatch is the documented
`EDWMM31.msh` case. Dynamic value-zero records and type-3 animation conclusions
in this document are binary-corpus observations rather than source-level
reconstructions.

### Tools

Bytefield SVG descriptions are provided in `MSH_STATIC.bytefield.edn` and
`MSH_DYNAMIC.bytefield.edn`, with rendered copies in the corresponding `.svg`
files. Regenerate them with:

```bash
npx bytefield-svg --source MSH_STATIC.bytefield.edn --output MSH_STATIC.bytefield.svg
npx bytefield-svg --source MSH_DYNAMIC.bytefield.edn --output MSH_DYNAMIC.bytefield.svg
```

Run the supplied parser against one or more files:

```bash
python3 msh_dump.py EDUST1.msh EDWCA1.msh EDBBC.msh UCSUHL3.msh edbpp.msh LCUFG3.msh EDUA22.msh
python3 msh_dump.py --details EDWCA1.msh
```

`msh_dump.py` uses every serialized count and stride, follows the static next-record chain
or dynamic child counts, and requires the final cursor to equal EOF. It also
validates the static trailing-unwind invariant, decodes reverse-packed animation
frame counts, and reports active boxes and attachments. It expects the archive
preamble and deliberately does not accept raw `MESH` payloads such as
`EDUOBS.msh` and `UCSUOBS.msh`. `EDUST1`, `EDWCA1`, `EDBBC`, `UCSUHL3`,
`edbpp`, and `LCUFG3` validate at `0xB02`, `0xF3E`, `0x96A3`, `0x23FC8`,
`0x4C59`, and `0x470A` respectively. `EDUA22` validates at `0x206F`.

Do not use whole-file hashes as a converter regression test:

- The GUID always changes.
- A nonzero static next-record marker is a live heap address and changes by
  process.
- Baked animation/matrix floats can vary at low bits across x87/runtime
  environments. The static `EDUST1` conversion was otherwise byte-identical;
  the animated `EDWCA1` retained exactly the same structure and counts under
  Wine but showed expected floating-point differences from the historical
  output.
